4. Cases where the AI was wrong, incomplete or misleading

Example 1 — Wrong reference baseline. In step 1 the AI wrote “the reference is the median baseline”, because the median is the constant that minimises MAE. That is statistically true, but the assignment defines the threshold with MAE_mean, the mean-predictor baseline. Using the median (MAE 14.66) instead of the mean (14.99) would have made the threshold silently stricter than required.
Found: by comparing the code with the assignment text (pasted comment, 22:48). Fixed: threshold now uses MAE_mean; the median is reported only as an extra reference; per-group bias recomputed against the mean.

Example 2 — Code that violated the core rule of a “green” project. The AI's first step-2 code trained the main model outside the CodeCarbon tracker, ran the tracker with save_to_file=False (no emissions.csv), and re-trained an identical copy of the main model as the ablation baseline (wasted energy). Found: by an external review, which I then checked line by line with the AI. Fixed: every training and evaluation now goes through run_experiment(), which always measures it and appends a row to emissions.csv; the ablation reuses the main run. The review itself also contained a false claim (that final_emissions_data was read before stop()). The code showed the read was already after stop(), so I rejected that point. Lesson: the reviewer's claims also had to be checked against the code. Honest consequence: the first unmeasured main training (25.6 min) and a stopped ablation are missing from the emissions log; I chose not to estimate them, so that the measured data contains no guessed values.

Example 3 — Doing more than asked, and breaking fairness. I asked to retrain my CNN with 40 epochs and intended only to change MAX_EPOCHS. The AI instead left MAX_EPOCHS = 20, added a separate 40-epoch path with new run names only for my own CNN, and started the training in the background. That would have given my model a larger training budget than the standard models (an unfair comparison), and a background run would have overlapped with my own runs and corrupted the energy measurement.
Found: I noticed MAX_EPOCHS was still 20 and asked what had been changed. Fixed: the AI stopped its run (no epoch completed, no emissions row) and reverted its path. I set MAX_EPOCHS = 40, insisted that all models be retrained under the same conditions, and ran the steps myself. The fairness check now shows each model's own epoch limit and warns if they differ.

Example 4 — Bug hidden by testing on different data. Step 4 crashed on my machine with TypeError: boolean value of NA is ambiguous. The AI had filled missing note columns with pd.NA, and pd.NA == "no" is neither True nor False. Its own test passed because it ran on the archived session, whose columns were filled. Fixed: None instead of pd.NA; I confirmed that the measurements made before the crash were saved and not duplicated (row count unchanged).

Example 5 — Incomplete: no warning about measurement conditions. The AI started long trainings in the background overnight but did not tell me to fix the power settings, disable sleep, or avoid other runs. A run I started manually from the terminal then overlapped with its background runs. The CodeCarbon rows show the effects: the 64 px run used a low-power mode (~9 W CPU vs. ~33–38 W later), the laptop slept ~5 h during the 48 px run (epoch 2 took 17,799 s), and the ResNet/MobileNet runs overlapped. Found: by reading duration and CPU-power columns per run. Fixed: I applied fixed Windows power settings, re-ran everything one run at a time, kept session 1 in an archive with per-run notes, and compared the two sessions. Example: own CNN 64 px went from 38.8 min / 12.20 Wh to 9.5 min / 7.64 Wh. This showed that measurement conditions can change energy by as much as the differences between models.

Example 6 — “No code change” was not respected. When translating strings to English, the AI also changed three f-string expressions: it added a .lower() and reordered variables in two messages. Found: by an AST comparison of old and new files (all strings replaced by a placeholder), which reported “CODE DIFFERS” for those lines. Fixed: reverted; the re-check showed only strings, comments and three intended pandas column names had changed. The AI's own Turkish-leftover detector also gave false positives, because a case-insensitive regex matched the Turkish dotless “ı”; that was fixed too.

5. How I verified the AI output

  • Shape and size checks: check_model() runs a forward pass and prints the tensor shape after every stage (64 → 32 → 16 → 8 → 4 px, output (N,)), which I checked against the design; the parameter count (294,129) and per-layer output sizes in the layer table come from the actual model, not from text.
  • Hand calculations: receptive field per layer (RF 68 at the last conv); FLOPs = 2 × MACs (53.7 M MACs ↔ 107.3 MFLOPs from FlopCounterMode); thresholds 1.15 × 4.937 = 5.677 and 0.6 × 14.99 = 8.99; ratio 5.81 / 4.94 = 1.177; project total = sum of all emissions.csv rows (deduplicated by run_id).
  • Documentation and logs: checked that allow_multiple_runs exists in CodeCarbon 3.3.2; confirmed the claim “CPU energy is read from RAPL” with CodeCarbon's own info log (CPU Tracking Method: Windows EMI; RAM is estimated), quoted in train_utils.py; checked PyTorch's default conv init (kaiming_uniform_(a=√5)).
  • Reproducibility: the 48 px model trained with a 40-epoch limit reproduced the 20-epoch run's first 20 epochs exactly (val MAE 5.808099…), so the seed and data pipeline are deterministic.
  • Smoke tests without side effects: after big edits, all steps were run against archived models in a scratch folder, with checks that emissions.csv was unchanged and data/test_usage.json was not created (test set still unopened).
  • AST diff for the translation (Example 6), and visual inspection of every figure. This caught overlapping labels in the Pareto plot twice before the layout was correct.

What it sped up. Boilerplate that would have taken me days: the CodeCarbon wrapper, tables, plots, the layer/receptive-field report, archiving and session comparison, and the translation. It was also fast at reading training histories and proposing analyses. The flip-TTA / ensemble idea took the model from failing to passing the threshold at no extra training energy.

What it made harder. The AI often made confident decisions beyond the request: the median baseline, a separate 40-epoch path, and starting long runs itself. I had to read every change and ask “what exactly did you change?”. Runs started by the AI in the background and by me in a terminal could overlap, which made the energy measurements harder to control (session 1). In a green-AI project the AI's own compute is also not counted in emissions.csv.

What I would do differently. (1) Apply the measurement settings and run every training myself from the first day. (2) Give the AI the acceptance criteria and fixed experimental conditions (epoch budget, baseline definition) in writing before any code. (3) Ask for a verification script with every non-trivial change, not afterwards. (4) Keep this log while working instead of reconstructing it from the transcript.
